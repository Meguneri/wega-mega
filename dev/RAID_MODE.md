# Режим «Рейд» (экстракшн, PvEvE) — Фаза 1

Экстракшн-лутер-шутер в духе Escape from Tarkov поверх инфраструктуры арены.
Кор-луп: **заход → лут/бои → экстракт по таймеру = выжил со шмотом; смерть = шмот остаётся
лутом на локации.** Персистентность: стэш, валюта и статистика рейдера сохраняются в локальной БД
между раундами; карта-база загружается для каждого игрока отдельно.

## Что уже работает (Фаза 1)

- `RaidController` — предзагрузка карты рейда, таймер рейда, объявления старта/конца.
- `RaidEntryButton` — вход с хаба: переносит мобов с грида кнопки на спавны рейда, стартует таймер.
- `RaidSpawnMarker(1..3)` — точки появления (инсерт).
- `RaidExtractionPoint` — зона экстракта: стой `extractTime` сек → эвакуация на хаб (с попапом %).
- `RaidReturnMarker` — точка возврата выживших на хабе.
- Потеря шмота при смерти — штатное поведение SS14 (тело роняет инвентарь), отдельного кода нет.

Код: `Content.Server/_Wega/Raid/` (компоненты + `RaidControllerSystem` + `RaidExtractionSystem`).
Прототипы: `Resources/Prototypes/_Wega/Entities/Markers/Spawners/Conditional/raid.yml`.
Локаль: `Resources/Locale/ru-RU/_wega/raid/raid.ftl`.

## Что уже работает (Фаза 2 — экономика)

Тарковский цикл «вынес лут → получил деньги → закупился»:

- **Лут на карте** — спавнеры `RaidLootSpawnerCommon/Rare/Epic` (в `raid_loot.yml`): по загрузке карты
  с шансом спавнят случайные предметы, метят их `RaidLoot` и самоудаляются. Стоимость предметов —
  штатная карго-оценка (`PricingSystem`).
- **Награда за вынос** — при экстракте суммируется стоимость вынесенной добычи (с меткой `RaidLoot`),
  лут «продаётся» (с него снимается метка) и игрок получает **телекристаллы на персистентный счёт**.
  Стартовое снаряжение метки не имеет — остаётся при игроке. Настройки в `RaidController`:
  `creditsPerTc`, `baseReward`, `maxReward`.
- **Хаб-магазин** — `RaidShopTerminal` (на базе `StorePresetFullArsenal`): весь арсенальный пул за ТК.
  Баланс берётся напрямую из персистентного стэша, физические ТК вставлять не нужно.

Код Фазы 2: `RaidLootComponent`, `RaidLootSpawnerComponent`/`System`, расширенный `RaidControllerSystem`
(`ExtractRaider` считает и продаёт лут, выдаёт ТК).

## Персональная база (hideout)

Каждый игрок получает **собственную изолированную карту-базу** (`Resources/Maps/_Wega/Raid/hideout.yml`):
- Личный схрон (`RaidStashBox`) — сохраняется между раундами.
- Персональный магазин (`RaidShopTerminal`) — баланс берётся из персистентного стэша.
- Кнопка входа в рейд (`RaidEntryButton`).
- Точка спавна игрока (`RaidHideoutSpawnMarker`).

База загружается при коннекте игрока и удаляется при дисконнекте / рестарте раунда. Возврат после
успешного экстракта идёт не на общий хаб, а на личную базу. Другие игроки не попадают на чужую базу
(каждая — отдельный `MapId`).

## Как собрать режим (маппинг)

1. **Сделай карту-локацию рейда** в ин-гейм редакторе (как делаются арены) и сохрани, например,
   в `Resources/Maps/_Wega/Raid/raid_location.yml`. На ней расставь:
   - несколько `RaidSpawnMarker`, `RaidSpawnMarker1`, … (точки инсерта по краям);
   - одну или несколько `RaidExtractionPoint` (зоны выхода, обычно по углам/в укрытиях).
2. **На хаб-карте** поставь только:
   - один `RaidController` и в его поле `raidMap` пропиши путь к карте из п.1.
   - `RaidEntryButton` — опционально, для входа прямо с хаба.
   `RaidReturnMarker` и `RaidShopTerminal` больше не нужны на хабе: у каждого игрока свои на базе.
3. Запусти раунд, подключись — игрока телепортирует на его персональную базу. Нажми кнопку входа
   на базе → телепорт в рейд, пойдёт таймер. Встань на `RaidExtractionPoint` — эвакуирует обратно
   на базу.

> Базовый путь карты в прототипе (`/Maps/_Wega/Raid/raid_location.yml`) — заглушка.
> Пока такой карты нет, контроллер залогирует ошибку загрузки и вход работать не будет.

## Настройки

- `RaidController.raidDuration` — длительность рейда (сек, по умолчанию 600 = 10 мин).
- `RaidExtractionPoint.range` / `extractTime` — радиус зоны и время стояния для эвакуации.
  По умолчанию экстракт **мгновенный** (`extractTime: 0.1`): достаточно зайти в радиус зоны.
  Точка экстракта видна как зелёный маяк (`PointLight` + glow-спрайт).

Маппинг: расставь по локации `RaidLootSpawnerCommon/Rare/Epic` (или один `RaidLootField` для
авто-разброса по всему гриду).

## Что уже работает (Фаза 3 — AI/скавы, PvEvE)

- **Фракции** (`_Wega/ai_factions.yml`): `Skav` и `RaidBoss`. Скавы враждебны к игрокам
  (`NanoTrasen`/`Syndicate`), но **не к боссам и не к своим** (нейтралитет = отсутствие в `hostile`).
  Боссы тоже бьют игроков, но скавов не трогают.
- **Дикие** (`_Wega/Entities/Mobs/NPCs/skav.yml`): несколько типов, рандомизируемых на спавне:
  - `MobSkav` — «обычный» дикий со случайным снаряжением (мачете / топор / копьё / нож / тулбокс /
    кустарный пистолет / ПП), медленный, косой.
  - `MobSkavRusher` — быстрый и хрупкий ближнобойщик (нож / копьё / мачете).
  - `MobSkavSniper` — медленный, точный дальнобойщик с винтовкой.
  - `MobSkavHeavy` — бронированный тяжеловес с ПП/дробовиком и повышенным здоровьем.
  Спавнер `RaidSkavSpawner` выдаёт обычных/забегунов чаще, снайпера/тяжеловеса — реже
  (`rarePrototypes`). Меткость задаётся **типом** (`RaidSkavAccuracy`), а не стволом; стволы
  «изношенные» (`*Skav`) — дешёвые. Поведение (`RaidSkavCompound`): бегство при ранах → бой →
  **падальщичество** (ищут и подбирают валяющиеся предметы) → **патруль** (блуждание). В рюкзаке
  ценность + запасные магазины — падают с трупа.
- **Огнестрел у Диких** (`RaidSkavRangedCompound` + `RaidSkavAutoReload`): стреляют пока есть патроны;
  магазин кончился → сами достают запасной из сумки и перезаряжаются; запасные кончились → ствол
  пустой → ближний бой прикладом/кулаками. Без ванильного цикла «бросил-поднял пустой ствол»
  (кастомный ранед-компаунд без веток дропа/подбора). Босс — то же, но точный.
- **Боссы** (`MobSkavBoss`/`MobSkavBossShotgun`/`MobSkavBossSMG`): толстые (500 HP), точные (обычные
  стволы — АК/дробовик/Дрозд), **стоят и охраняют точку** (`RaidBossCompound` без блуждания), имя
  случайно-уникальное («Вожак «Бешеный Кабан»» через `RandomMetadata` + датасеты), снаряжение всегда
  лучше (бронежилет, шлем). Бонус-дроп с трупа: золото, алмаз, АК.
- **Болтовня** (`RaidSkavChatterComponent`/`System`): живые скавы изредка выкрикивают случайные
  реплики («Чую мясо...», «Лут! Моё!»), боссы — свои, реже и весомее. Интервал/шанс рандомные.
- **Боевые барки + зов стаи** (`RaidSkavCombatReactionSystem`): в бою скав выкрикивает боевую
  реплику («Враг! Бей его!») и «зовёт» соседних скавов в радиусе 12 — добавляет им цель в память
  агра (`NPCRetaliation`+`FactionException`), чтобы стая запоминала и преследовала жертву (в т.ч.
  после потери из вида). Кулдаун против спама.
- **Бегство** (`RaidSkavCompound` + `LowHealthPrecondition`): дикий скав, набрав ~половину урона до
  крита, отходит от врага на 10–14 тайлов (`MaintainRangeOperator`) вместо драки. Босс НЕ бежит
  (его `RaidBossCompound` без ветки бегства) — стоит насмерть.
- **Лут с трупа** (`RaidLootCarrierComponent`/`System`): при смерти скава всё его снаряжение метится
  `RaidLoot` — игрок может снять с трупа и вынести за деньги. Босс дополнительно роняет
  гарантированный бонус (золото/алмаз). Death-акидайзер скавам намеренно не ставится.
- **Спавнеры** (`raid_skav.yml`): `RaidSkavSpawner` (с шансом — стрелок), `RaidSkavBossSpawner` —
  на базе штатного `RandomSpawner`, спавнят при загрузке карты и самоудаляются.

## Что уже работает (Фаза 1.1 — напряжение и корректность)

- **Предупреждения о таймере**: за `warningTimes` секунд до конца (по умолчанию 300 и 60) идёт
  объявление «на выход». Настраивается на `RaidController`.
- **Смерть по таймеру (MIA)**: кто не успел эвакуироваться к концу рейда — добивается `miaDamage`
  (по умолчанию Asphyxiation 500), теряет всё. Убери блок `miaDamage` для мягкого режима.
- **KIA-фид**: погибший в рейде выбывает из списка рейдеров с объявлением.
- **Досрочное завершение**: если вышли/погибли все рейдеры — рейд заканчивается, не дожидаясь таймера.
- **Повторяемость рейдов**: контроллер на старте КАЖДОГО рейда чистит лут и скавов прошлого захода
  и заново заселяет локацию через лут-поля (`RaidLootField` для добычи, `RaidSkavField` для скавов).
  Каждый заход стартует с полной, нетронутой локации (а не один свежий рейд за раунд).
- **Отключения игроков**: если рейдер дисконнектится во время активного рейда, его персонаж
  экстренно возвращается на хуб. Стартовое снаряжение остаётся при нём, но весь найденный в рейде
  лут (`RaidLoot`) остаётся на локации. Мёртвые рейдеры не телепортируются — их тело остаётся
  лутом, как при обычной смерти.

## Быстрый запуск (тест без редактора)

Для проверки режима есть тестовый контроллер `RaidControllerTest`: он грузит готовую арену
(`arena_duel_31`) как локацию рейда, ставит короткий таймер (3 мин) и **сам расставляет** на ней
спавны входа, точку экстракта и поля лута/скавов (`autoSetup`). Запуск — пара спавнов через админку:

1. Запусти игру (сервер + клиент), старт раунда, права админа.
2. Открой меню спавна сущностей (F5 / «Spawn entities») и заспавни рядом с собой:
   - `RaidControllerTest` — при спавне грузит карту рейда и авто-настраивает её;
   - `RaidEntryButton` — кнопка входа (можно на общем хабе).
3. Подключись/возродись — игрока телепортирует на персональную базу со схроном и магазином.
   Активируй кнопку входа на базе → телепорт в рейд, пойдёт таймер 3 мин, локация заселится
   лутом и скавами.
4. Убивай скавов, собирай лут, встань на точку экстракта ~10 сек → возврат на свою базу с наградой ТК.
5. Не успеешь за 3 минуты — MIA (смерть, потеря всего). Вышли/погибли все — рейд закончится раньше.

> ⚠️ Кнопка входа утаскивает в рейд ВСЕХ мобов на гриде кнопки и на всех гридах-убежищах.
> Для чистого теста жми её в одиночном раунде. `RaidControllerTest` — только для отладки,
> в реальный режим ставь обычный `RaidController` со своей картой.

## Полноценный запуск: карта делается в редакторе

Подтверждено: тайлы карт SS14 — это base64-кодированные бинарные чанки (`MapGrid.chunks[].tiles`),
руками валидную карту не написать. Поэтому `raid_location.yml` и расстановка маркеров — работа в
ин-гейм редакторе (как все наши арены). Без неё режим не запускается (контроллер пишет `Warning`).

Маппинг (минимум на карте рейда): спавны входа, точки экстракта, один `RaidLootField` и один
`RaidSkavField`. Контроллер сам заселит локацию на каждом заходе.

## Персистентность между сессиями (локальная БД — сделано, облако — TODO)

> Базовая персистентность реализована: прогресс сохраняется в локальной БД сервера и восстанавливается при коннекте игрока. Облачный backend/S3 оставлен на Phase 2.

Ниже — проверенный план, по которому реализован локальный вариант. Конкретные классы/файлы указаны.

---

### 1. Архитектура: сервер-авторитарная + облако через backend

Самый надёжный вариант — **backend-сервис + S3-совместимое хранилище** (MinIO / AWS S3 / Yandex Object Storage / Selectel):

- В облако складываются только блобы — не чувствительные операции.
- `Content.Server` общается с backend по HTTPS/REST, backend отвечает за аутентификацию, валидацию, запись в S3 и кэш.
- Никаких AWS-ключей в коде клиента или в открытых CVars; credentials — только на сервере.
- Локальная БД (`Content.Server.Database`) используется как кэш и fallback при недоступности backend/S3.

Если backend не хочется — можно положить блобы прямо в БД (`byte[]`/`jsonb`), но тогда теряется переносимость между серверами и растёт нагрузка на БД.

### 2. Схема данных

#### 2.1. Таблица в `Content.Server.Database`

Добавить сущность `RaidStash` (аналогично `Achievement` в `Content.Server.Database/Model.cs`):

[Table("raid_stash"), Index(nameof(PlayerUserId))]
public class RaidStash
{
    [Required, Key, ForeignKey("Player")]

### 3. Сериализация предметов

Robust уже умеет сохранять сущности в YAML: `MapLoaderSystem.SerializeEntitiesRecursive`.

#### 3.1. Сохранение стэша

Создать на хабе невидимый «stash-контейнер» (например, специальный `RaidStashBox` entity), в который складывать всё, что игрок хочет сохранить. Затем:

```csharp
var (node, _) = _mapLoader.SerializeEntitiesRecursive(
    new HashSet<EntityUid> { stashBoxUid });

var yaml = node.ToYaml();
// YamlDocument + YamlStream.Save(...) -> string
```

`SerializeEntitiesRecursive` рекурсивно сохраняет детей, поэтому внутри контейнера будут работать:
- `StackComponent.Count`,
- `BatteryComponent.LastCharge`,
- `GunComponent` + дети-магазины,
- `SolutionContainerManagerComponent`,
- вложенные сумки и их содержимое.

Ограничения:
- не сохранятся компоненты с `[ComponentRegistration(Unsaved = true)]`;
- прототипы с `MapSavable = false` отклонятся;
- runtime-состояние (текущие цели NPC, DoAfter и т.п.) не сохраняется.

#### 3.2. Загрузка стэша

```csharp
if (_mapLoader.TryLoadEntity(reader, source, out var stashBoxUid))
{
    // Переместить загруженный контейнер в null-space или на хаб,
    // затем отдать игроку через инвентарь/хранилище.
}
```

Перед десериализацией валидировать каждый прототип через `_prototype.HasIndex<EntityPrototype>(...)`, чтобы вайп или удаление прототипа не ломали загрузку.

### 4. Жизненный цикл: когда грузить и сохранять

#### 4.1. Загрузка при коннекте

Подписаться в `RaidStashSystem` на `UserDbDataManager`:

```csharp
public override void Initialize()
{
    _userDbData.AddOnLoadPlayer(LoadStashAsync);
    _userDbData.AddOnPlayerDisconnect(SaveStashAsync);
}
```

`LoadStashAsync(NetUserId)`:
1. Попробовать загрузить с backend/S3 по `session.UserId`.
2. Если backend недоступен — взять `RaidStash` из локальной БД.
3. Распарсить снапшот, провалидировать прототипы, сохранить в памяти (`Dictionary<NetUserId, RaidStashSnapshot>`).

#### 4.2. Материализация на хабе

Когда игрок спавнится на хабе (или открывает магазин), создать/открыть его stash-контейнер из кэшированного снапшота.

Если снапшот пустой — создать новый пустой контейнер и начальный баланс валюты (если нужно).

#### 4.3. Сохранение при экстракте

В `RaidControllerSystem.ExtractRaider` (`Content.Server/_Wega/Raid/Systems/RaidControllerSystem.cs:343`):

```csharp
// 1. Посчитать стоимость лута (уже есть).
// 2. Зачислить валюту в снапшот.
// 3. Переложить предметы с меткой RaidLoot в stash-контейнер.
// 4. Сохранить снапшот: сначала в БД, потом отправить на backend/S3.
// 5. Только после успешного сохранения удалить лут и телепортировать игрока.
```

Это гарантирует, что при ошибке записи игрок не потеряет лут (атомарность на уровне сервера).

#### 4.4. Сохранение при дисконнекте

В `RaidControllerSystem.OnPlayerDetached` (уже есть обработка дисконнекта):
- если игрок был в активном рейде — вернуть на хуб без лута (уже реализовано);
- в любом случае сохранить текущий stash-снапшот.

#### 4.5. Сохранение при конце раунда

Подписаться на `RoundRestartCleanupEvent` (`Content.Shared/GameTicking/RoundRestartCleanupEvent.cs`):

```csharp
SubscribeLocalEvent<RoundRestartCleanupEvent>(_ => FlushAllStashes());
```

Сохранить все изменённые снапшоты **до** `EntityManager.FlushEntities()`.

### 5. Экономика: от физических ТК к персистентному балансу

Сейчас награда выдаётся физическими телекристаллами (`_stack.SpawnMultipleNextToOrDrop`). Это позволяет дюпать/терять валюту в раунде.

#### 5.1. Персистентный баланс

- Хранить `Currency` в `RaidStashSnapshot`.
- В `ExtractRaider` вместо спавна ТК увеличивать `Currency["Telecrystal"]`.
- При спавне игрока на хабе выдать ему физические ТК из баланса **один раз**, чтобы он мог тратить их в магазине.
- Либо переделать `RaidShopTerminal` так, чтобы он списывал напрямую из `RaidStashSnapshot.Currency`, а не из инвентаря.

#### 5.2. Магазин

`StoreSystem`/`SharedStoreSystem` (`Content.Server/Store/Systems/StoreSystem.cs`) умеет работать с `StoreComponent.Balance`. Два варианта:

1. **Простой**: при открытии терминала синхронизировать `StoreComponent.Balance` со снапшотом, а после покупки — записать обратно.
2. **Надёжный**: создать отдельный `RaidStoreSystem`, который не использует `StoreComponent.Balance`, а сразу списывает валюту из `RaidStashSnapshot` и спавнит купленный предмет.

Рекомендуется второй вариант — меньше точек рассинхронизации.

### 6. Облачное хранилище: конкретная реализация

#### 6.1. Backend-сервис (рекомендуется)

Минимальный REST-сервис (ASP.NET Core / FastAPI / Node):

```
POST /api/raid-stash/{userId}      -> сохранить блоб (тело: JSON, version, checksum)
GET  /api/raid-stash/{userId}      -> получить блоб
DELETE /api/raid-stash/{userId}    -> вайп (админка)
```

Backend:
- проверяет подпись запроса (HMAC по серверному секрету);
- кладёт/читает блоб в S3 по ключу `raid-stash/{userId}.json`;
- ведёт `ETag`/version для conflict resolution;
- возвращает 304, если версия не изменилась;
- пишет последнюю версию в Redis/DB для hot cache.

#### 6.2. Прямой S3 из Content.Server

Если backend лишний:

```csharp
using Amazon.S3;
using Amazon.S3.Model;

var client = new AmazonS3Client(accessKey, secretKey, new AmazonS3Config
{
    ServiceURL = "https://s3.example.com", // MinIO / Yandex / etc.
    ForcePathStyle = true
});

await client.PutObjectAsync(new PutObjectRequest
{
    BucketName = "wega-raid",
    Key = $"stash/{userId}.json",
    ContentBody = json,
    ContentType = "application/json"
});
```

Нужно добавить `AWSSDK.S3` (или `Minio`) в `Content.Server.csproj`.

Недостаток: секреты придётся держать на игровом сервере; утечка = доступ ко всем стэшам. Backend вариант безопаснее.

#### 6.3. Fallback

В `RaidStashSystem`:

```csharp
async Task SaveAsync(NetUserId userId)
{
    await SaveToLocalDbAsync(userId);          // всегда
    try { await SaveToBackendAsync(userId); }  // лучший effort
    catch (Exception e) { _sawmill.Error($"Cloud save failed: {e}"); }
}
```

При загрузке:
1. Попробовать backend (актуальные данные).
2. Если недоступен — локальная БД.
3. Если и её нет — пустой стэш.

### 7. Безопасность и защита от дюпа

- **Только сервер пишет** — клиент никогда не обращается к backend/S3.
- **Валидация прототипов** — каждый предмет из снапшота проверяется на `HasIndex<EntityPrototype>`.
- **Чексумма** — Blake2B/SHA-256 над `Payload`. Хранится в БД и в блобе; при загрузке пересчитывается.
- **Версионирование** — `Version` инкрементируется при каждом сохранении; конфликты разрешаются на backend (`last-write-wins` или server-side merge).
- **Атомарный экстракт** — сначала сохраняем стэш, потом удаляем лут и телепортируем игрока.
- **Rate limiting** — не чаще одного сохранения на игрока в N секунд (кроме дисконнекта/конца раунда).
- **Бан/вайп** — консольные команды `raidstash_wipe <userId>`, `raidstash_give <userId> <currency> <amount>`.

---

### 8. Порядок внедрения

1. **DB**: `RaidStash` таблица + миграции + `ServerDbManager` методы.
2. **Снапшот**: record `RaidStashSnapshot` + JSON сериализация.
3. **StashSystem**: загрузка/сохранение через `UserDbDataManager`, кэш в памяти.
4. **Сериализация предметов**: `MapLoaderSystem.SerializeEntitiesRecursive`/`TryLoadEntity`, тестовый stash-контейнер.
5. **Экономика**: персистентный баланс, замена физических ТК на запись в снапшот.
6. **Магазин**: `RaidStoreSystem` списывает валюту из снапшота.
7. **Cloud**: backend + S3, fallback на локальную БД.
8. **Админка**: команды вайпа/выдачи, веб-панель (опционально).
9. **Тесты**:
   - интеграционный тест: экстракт -> сохранение -> реконнект -> стэш на месте;
   - тест на дюп: попытка экстракта при недоступном backend не удаляет лут.

---

### 9. Альтернатива без облака

Если облако отложено — хранить блобы в `RaidStash.Payload` (`jsonb`/`TEXT`). Это работает из коробки, но:
- не переносится между серверами;
- требует бэкапов БД;
- при большом стэше растёт размер БД.

Для первой playable-итерации это приемлемо; cloud layer добавляется позже без изменения схемы снапшота.

## Как загружается стэш игрока

Персистентность реализована через `RaidStashSystem` + `UserDbDataManager` (тот же паттерн, что и для префов/плейтайма):

1. **Регистрация.** `RaidStashSystem` подписывается на `AddOnLoadPlayer`, `AddOnFinishLoad`, `AddOnPlayerDisconnect` и `PlayerAttachedEvent`.
2. **Коннект.** `UserDbDataManager` параллельно грузит данные всех подписчиков. Для стэша вызывается `_db.GetRaidStashAsync(session.UserId)`; снапшот десериализуется из JSON и проверяется чексумма. Если записи нет — создаётся пустой стэш.
3. **Ожидание.** `GameTicker` ждёт `WaitLoadComplete(session)` перед спавном персонажа, поэтому стэш уже в памяти.
4. **Персональная база.** В `OnFinishLoad` для игрока создаётся отдельный `MapId`, на него загружается
   `Resources/Maps/_Wega/Raid/hideout.yml`, и на гриде базы спавнится личный `RaidStashBox` с
   восстановленными предметами из `stash.Items`.
5. **Телепорт на базу.** Когда моб привязывается к игроку (`PlayerAttachedEvent`), персонаж
   телепортируется на маркер `RaidHideoutSpawnMarker` своей базы.
6. **Сохранение.** При дисконнекте, перед заходом в рейд и при `RoundRestartCleanupEvent` содержимое схрона сериализуется в YAML и вместе с валютой/статистикой пишется в БД через `_db.SaveRaidStashAsync`. После сохранения личная карта-база удаляется.

## Если играет другой игрок

Каждый аккаунт получает **свой** экземпляр базы (`hideout.yml`) на отдельном `MapId`. Схрон, баланс
ТК и статистика привязаны к `NetUserId`. Игроки не видят и не попадают на чужие базы: их телепортирует
только на свою, а кнопка входа на чужой базе недоступна физически (другие карты). Если несколько
игроков играют с одного клиента/аккаунта, они разделяют один стэш.
